# Learn From Software You Didn't Write

Open source software က အသုံးပြုဖို့ပဲ မဟုတ်ပါဘူး။ ကိုယ်မရေးထားတဲ့ software ကို ဖတ်ပြီး **တခြား developer တွေရဲ့ ဆုံးဖြတ်ချက်တွေကနေ သင်ယူနိုင်ပါတယ်**။

## 01 — Start with the README
“ဒီ project က ဘာ problem ကို ဖြေရှင်းတယ်လို့ claim လုပ်ထားတာလဲ?” လို့ အရင်မေးပါ။ README က project ရဲ့ mental model ကို အမြန်ရစေပါတယ်။

## 02 — Read the directory tree
Folder structure ကို ကြည့်ပြီး “တကယ် code က ဘယ်မှာရှိတာလဲ?” ဆိုတာရှာပါ။ File တစ်ဖိုင်ချင်းစီ မဖတ်ခင် map အရင်လုပ်တာပါ။

## 03 — Find one real PR
Pull Request တစ်ခုကို ရွေးပြီး ဘာပြောင်းခဲ့လဲ၊ ဘာကို reject လုပ်ခဲ့လဲ၊ ဘာကြောင့် ဒီ solution ကို ရွေးခဲ့လဲဆိုတာ ကြည့်ပါ။

## 04 — Skim the test suite
သူတို့အတွက် “စစ်ဆေးရကျိုးနပ်တဲ့ behavior” က ဘာလဲဆိုတာ tests က ပြောပြနိုင်ပါတယ်။

## ဘာတွေ သင်ယူနိုင်လဲ?

- Production/real-world မှာ survive လုပ်လာတဲ့ architecture
- နေ့တိုင်းရေးနေသူတွေရဲ့ naming habits
- လက်တွေ့ test strategy
- နောက်လူဖတ်ဖို့ ရေးထားတဲ့ documentation
- Trade-off တွေကို ဘယ်လို ဆွေးနွေးဆုံးဖြတ်ကြလဲ
- Maintainers တွေအတွက် တကယ်အရေးကြီးတာ ဘာလဲ

Open source project ထဲကို contribution မလုပ်နိုင်သေးလည်း သင်ယူလို့ရပါတယ်။ အကောင်းဆုံးအစကတော့ **ကိုယ်နေ့တိုင်းသုံးနေတဲ့ repo** တစ်ခုပါ။ သုံးနေပြီးသားဆိုတော့ မေးစရာမေးခွန်းတွေက ကိုယ့်မှာ ရှိပြီးသားဖြစ်လို့ပါ။

##

ကိုယ်မရေးထားတဲ့ software ကို ဖတ်တဲ့အခါ တခြား developer တွေက real-world constraint တွေအောက်မှာ ဘယ်လို decision ချခဲ့လဲဆိုတာ မြင်ရပါတယ်။ Compatibility code, bug တစ်ခုကြောင့် ရှိနေတဲ့ test, public API ဖြစ်လို့ မပြောင်းနိုင်တဲ့ interface, benchmark ကြောင့် ထည့်ထားတဲ့ optimization စတာတွေကို တွေ့နိုင်ပါတယ်။

ဒါကြောင့် code တစ်ခုကို ပထမဆုံးမြင်တာနဲ့ “ဒီဟာက bad architecture” လို့ မဆုံးဖြတ်သင့်ပါဘူး။ Duplicate ဖြစ်နေတာကို တွေ့ရင်တောင် “ဘာကြောင့် ဒီလိုထားထားတာလဲ” လို့ အရင်မေးကြည့်ပါ။ Abstraction ထည့်လိုက်ရင် code ပိုရှုပ်သွားနိုင်ပါတယ်။ Stability ကို elegance ထက် ဦးစားပေးထားတာလည်း ဖြစ်နိုင်ပါတယ်။

Source code ဖတ်တဲ့အခါ အကုန်နားလည်ဖို့ မကြိုးစားပါနဲ့။ မေးခွန်းတစ်ခုရွေးပါ။ “ဒီ request က ဘယ်ကနေဝင်ပြီး ဘယ်ကိုသွားတာလဲ”, “authentication ကို ဘယ်မှာစစ်တာလဲ”, “retry ကို ဘယ်လိုလုပ်ထားတာလဲ” ဆိုပြီး တစ်ခုကိုပဲ လိုက်ကြည့်ပါ။ အဖြေတစ်ခုရသွားရင် နောက်မေးခွန်းတစ်ခု ဆက်မေးလို့ရပါတယ်။

ဒီလိုဖတ်ရင် source code က စာအုပ်ကြီးတစ်အုပ်လို မခံစားရတော့ဘဲ စုံစမ်းလေ့လာရတဲ့နေရာတစ်ခု ဖြစ်လာပါတယ်။
